# A7 One page and step 7a: every page drawn one way, the Assistant inside the shell — Plan

Date: 2026-11-04 · Status: **draft for the owner's review** · Baseline: `2026-11-01-platform-product-architecture-design.md`
plus amendment A7 (`2026-11-04-amendment-a7-one-page.md`, #110) and amendment A4
(`2026-11-03-amendment-a4-assistant-in-shell.md`, #78).

**Goal:** every page in Pi Hub and the Assistant reads as one product: the same head, strip, faceplate, Needs-you list,
rows and footer; plain words; risky fixes that ask first; designed loading, stale and down states. And the Assistant
button opens `/assistant` inside Pi Hub's shell instead of leaving it.

## Spec

- **A7, Decisions P1-P9 and Delivery.** Its delivery order: (1) appliance-ui minor, (2) Pi Hub pages in place,
  (3) Pi Hub step 7a, (4) Local AI's five pages. "A4's step 7a is a precondition for P1 to P8 on the Assistant's pages."
- **A4 / §11 step 7a:** "after 7's strip and 404 land. One LocalAI PR (requirements 2, 3, 4's listener, 7's route post),
  then one Pi Hub PR (`/assistant`, requirements 1, 4-8). LocalAI ships first."
- **Waits on:** step 7's strip and 404, which are on `origin/main` (below). A7 states no other dependency; none is added
  here.

## Done means

A7 gives no numbered criteria; A4 does for step 7a. Decision 1 proposes A7's.

**Step 7a (A4, "Acceptance (for step 7a)", quoted):**

1. "Desktop (Mac, Safari and Chrome): the button opens `/assistant` with the page's context over the composer; Local AI
   shows no bar of its own; reload keeps the Assistant page; back returns to the previous Pi Hub page in one step."
2. "Phone (iPhone Safari): five tabs; no second bar; the composer stays visible with the keyboard up; one scroller."

5. "Security checks: `curl -I https://assistant.…/` shows the `frame-ancestors` header; a page on another origin can't
   frame it; no `site_hub` route proxies to Local AI (test); a `postMessage` from another origin changes nothing."

**A7 (proposed in decision 1):**

6. P1: every page in the route table (`hub/static/js/routes.js`) and the Assistant's five pages draws head, strip, one
   faceplate, Needs you here (only when it has items), at most six sections, Open in, and the sources line, in that
   order. A test walks the route table and fails on a page missing a part or holding a second faceplate.
7. P2: Home, each area's Needs you here, the wall and the Assistant's Home use `ApplianceNeeds.renderList`. No item
   renders a bare "Open", and no same-origin link renders ↗.
8. P3/P4: every row uses the kit's lamp-right row; every page strip is underlined; filters and Settings' groups are chips.
9. P5: a test over rendered pages finds no `mac_lab`-style id, `/data/` path, "Merge pull request", "Materials" or
   "0°C" target. Versions names each release by its change and PR number.
10. P6: Alerts, the Assistant's Work and Health's recent fixes show one row per repeat group, with its count and range.
11. P7: Health's fixes sit in a closed "Fixes" section; each asks inline; Restart the Pi and Sign out use the danger
    button; toasts use the past tense of the button's verb.
12. P8: each page shows skeletons while loading; the stale and source-down states read as in the phrase table, seen

13. P9: the site map is generated from the rail's list and shows the Assistant's pages as pages in the shell.

## Decisions this plan makes (for the owner's review)

None changes the spec. If the owner disagrees with one, it changes here.

1. **A7's done criteria are 6-13 above**: one per decision, each checkable by a test or by looking. *Rejected:* "every
   page matches the prototype". The prototype has made-up data and can't be accepted against.
2. **The anatomy is kit CSS plus one small kit helper, not a framework.** The kit adds `.ui-page`, `.ui-page__head`,
   `.ui-strip` (underlined, `aria-current`), `.ui-chips`, `.ui-faceplate` (nameplate, lamp, readout, caption,
   readings, actions, optional aside), `.ui-sources`, and `.ui-row--lamp` (text left; lamp, value and action right).
   It also adds `confirm.js`, a ~40-line inline confirm. Each app keeps its own rendering code (Pi Hub's `h()`, Local
   AI's DOM code). *Rejected:* a shared JS page component. The two apps render differently, and the kit has so far
   been CSS plus small, pure helpers (`needs.js`, `palette.js`). *Trade-off:* each app has to arrange the parts in the
   right order. Criterion 6's test is what keeps them honest.
3. **Verb actions are kit phrase keys.** `needs.js` already takes words only from a phrase key (`needs.js:48-70`), so the
   verbs (`judge_it`, `open_printer`, `open_area` with `{name}`, `see_usage`, …) are added to the kit's phrase table and
   synced. The meta line becomes `since <time> · <area>` from `as_of` and `source`. *Rejected:* letting items carry
   free-text labels. Phrase keys are the platform's single owner of wording (section 9).
4. **Versions' name comes from the merge commit's PR title.** GitHub writes the PR title as the merge commit's body.
   Pi Hub's release recovery list reads `subject`, and for a merge it shows the body's first line plus `#N`. A commit
   that isn't a PR merge keeps its subject. *Rejected:* calling GitHub's API from the Pi. That adds a token and a
   network dependency for a label.
5. **Repeats group by the item's own key, per local day, in the page, not in the store.** An alert and its recovery
   share a cause key; a run repeats by its kind; a fix by its service. History and the API stay one entry per event,
   because they are the evidence. *Rejected:* merging rows in the database, which would lose the per-event times.
   H5 confirms the cause key in `hub/events.py` before it relies on it.
6. **A temperature with target 0 shows one number.** Bambu reports a target of 0 when the heater is off; that is "no
   target", not "target 0°C". *Rejected:* hiding the target only when the heater state says off. The field isn't
   always present.
7. **Step 7a stays third, as A7 orders, but its Local AI PR may merge early.** L1 (header, framed chrome, listener,
   route post) changes nothing for Local AI opened on its own (A4 requirement 9), so it can ship while the Pi Hub pages
   are in review. The Pi Hub `/assistant` PR still comes after the Pi Hub page PRs. *Rejected:* holding L1 back.
   Local AI being frameable by any site (the missing header) is a defect worth closing now.
8. **Until 7a lands, Assistant links keep ↗.** P2's "never ↗ for a page in the shell" applies once `/assistant`
   exists; before that, the Assistant is truly another origin. In 7a's Pi Hub PR, `resolveLink` sends
   `tool:assistant/#…` to `/assistant?to=…`, and Versions' Atlas link follows (A4, "Atlas").

axe output. Every Local AI PR goes through local CI and `npm run ship -- <PR>`.

### L1. Local AI: framed by Pi Hub (A4 requirements 2, 3, 4's listener, 7's route post)

- **Covers:** step 7a's Local AI half, in full. Can merge before H1-H5 (decision 7).
- **Change:** `Content-Security-Policy: frame-ancestors 'self' https://hub.rahe-home.duckdns.org
  https://home.home.arpa` on every response. Framed by a Pi Hub origin, there's no top bar, no "← Home" and no phone
  bar; the five pages show as a strip. A `message` listener checks the origin and treats the payload as text. On each
  route change, it posts the hash route to the parent, with the Pi Hub origin as the target.
- **Tests:** a header test; a test for the framed check (another origin → normal chrome); a listener test (another
  origin → no change; HTML → shown as text).
- **Evidence:** criterion 5's header and `postMessage` parts.

### H6. Pi Hub: `/assistant` in the shell (A4 requirements 1, 4-8)

- **Covers:** step 7a's Pi Hub half, in full. After L1 is live and H1-H5 have merged.
- **Change:** a route `/assistant` with `?context=` (300 characters at most) and `?to=`. The iframe is created on mount
  and removed on leave. Down state: `pc_off` or `assistant_down` and no frame; "Unknown" shows the frame; the 10 s load
  timeout gives `assistant_down` with "Try again". It sends `postMessage` with an explicit target origin. It updates
  the address with `replaceState` from the frame's route post. The frame has a title and takes focus; it is the only
  scroller. `resolveLink` sends `tool:assistant/#run/<id>` to `/assistant?to=run/<id>` (decision 8). Versions' Atlas
  link opens `/assistant?to=architecture?…`.
- **Tests:** requirement 1's test (no `site_hub` route proxies to Local AI); the down state for `Down` and `Unknown`;
  the address round trip; a link from another page reusing an open frame.
- **Evidence:** criteria 1-4 on the live hub, recorded by the owner.

### L2. Local AI: the five pages on P1-P6

# A35 M1a Mac side: sessions report, A34 imports, home-mcp reads structured decisions — Plan

## Goal

The Mac can describe an initiative and its live work in the shape Pi Hub's mission ledger will accept, without Pi Hub
having changed yet:
- Claude Code sessions that you attach to an initiative produce honest lifecycle events. Those events are queued safely
  whenever Pi Hub can't take them.
- A34 is written down once as a reviewed manifest file.
- Sessions can read structured decisions without breaking today's A33 read.

## What exists today (read on 24 Nov 2026)

**`~/.claude` is not under version control.** It is not a git repository. These live only on this Mac, with no review
or tests:
- `hooks/localai-progress.py`;
- `localai-chat/hook.py`, which is installed from LocalAI `host/claude-chat/install.sh`;
- the skills, including `owner-question`.

**The existing hook already derives safe labels.** `~/.claude/hooks/localai-progress.py`:
- `describe(tool, inp)` turns a tool call into a short label: a command's description, a file name, a host. It never
  sends content.
- It posts synchronously (urllib, 3 s timeout) to LocalAI on PostToolUse, SessionStart, UserPromptSubmit and Stop, and
  swallows every error.
- It is registered `async: true` in `~/.claude/settings.json`.

**home-mcp** (`a5b129e`): Python 3.12, uv, `httpx` and `mcp`, pytest.
- `hub.py`: `make_client`, and `get`, which returns `(data, failure)`, never raises.
- `decisions.py`:
  - `hub_key()` reads `HOME_MCP_HUB_KEY` or Keychain item `pi-hub-deploy-key` with a 5 s timeout.
  - `wrap()` defuses untrusted-text markers.
  - `_plain_ok` and `_shape_problem` fail the **whole** read when any row's `kind` is not `choice|text`
    (`KINDS = ("choice", "text")`).
  - 15 tests in `tests/test_decisions.py`.
- The MCP server is read-only (`READ_ONLY` annotations on every tool, `server.py:87-252`).

**Pi Hub** (`6997f58`): no `/api/missions/*` routes yet, and no `?v=2` on `/api/decisions`; both are M1b.
- `KEY_FOR` (`hub/releases.py:36`) has no `mission-claude` or `mission-importer`.
- `deploy/deploy-key.sh` makes deploy keys.

**print-lab** (`origin/main`): experiments are JSON records under `projects/<project>/experiments/E-NNN.json`.
- Fields include `schema: 1`, `record_type: "experiment"`, `id`, `project`, `question_text`, `hypothesis`, `prediction`
  and `findings[]`.
- The schema lives in `lab/records/schema.py`.

**M0 facts this plan relies on** (§21.1):
- Model is in no hook input; it is in the transcript's `message.model`.
- `effort.level` is in the tool and stop events.
- SubagentStart and SubagentStop carry `agent_id` and `agent_type`, and the Agent PostToolUse response carries
  `agentId`, `resolvedModel` and `totalTokens`.
- PermissionRequest fires in bypass mode on `permissions.ask` matches.
- A resumed session keeps its `session_id`.

## Decisions this plan makes (for the owner's review)

None changes the spec. If the owner disagrees with one, it changes here.

1. **The Mac code lives in home-mcp.** That covers the hook source, the skill, the spool drainer, the importer and the
   validator.
   - Layout:
     - a `home_mcp.mission` package;
     - a `home-mission` CLI entry point;
     - `claude/hooks/mission-report.py` and `claude/skills/mission/SKILL.md`;
     - `scripts/install-claude-mission.sh`, which symlinks them into `~/.claude`.
   - Why here: home-mcp already holds the hub client and the Keychain key code, and it runs on the Mac. Putting the code
     here gives it review and tests that `~/.claude` can't.
   - The MCP server stays read-only. The write path is the separate CLI, never an MCP tool.
   - Rejected:
     - Loose files in `~/.claude`: no review or tests.
     - LocalAI `host/`: Local AI is the PC's engine, and the ledger is Pi Hub's.
     - pi-hub `tools/`: every pi-hub test runs in the Pi's release, against the A34 P0 budget.
2. **The hook only appends to the spool; it never talks to the network.** `mission-report.py`:
   - uses only the standard library;
   - appends one line to `~/.claude/mission-spool.jsonl` under `fcntl.flock`;
   - then starts `home-mission drain` detached, if no drain holds `~/.claude/mission-drain.lock`;
   - exits 0 in all cases, with a 2 s self-limit.
   - Trade-off: there is no always-on agent, so with Pi Hub down, events wait for the next hook firing anywhere on the
     Mac. While they wait, M1b shows "No report since", which is honest.
   - Rejected: posting from the hook (adds latency to every tool call); a launchd drainer (another always-on process,
     not needed for correctness).
3. **The hook is installed off.**
   - The install writes `~/.claude/mission-config.json` with `{"enabled": false}`. While it is off, the hook does
     nothing except let `/mission attach` record its local binding.
   - M1b's acceptance turns it on, once `/api/missions/events/claude` exists.
   - Why: spooling for weeks against an endpoint that doesn't exist would only fill the 5 MB cap with stale events.
4. **The contract and manifest schema are owned by pi-hub; home-mcp keeps a synced copy.**
   - `docs/contracts/mission-events-v1.json` and `docs/missions/manifest.schema.json` live in pi-hub (spec §7.4).
   - home-mcp keeps copies under `src/home_mcp/mission/contract/`. A test pins their sha-256 to a named pi-hub commit,
     the same one-owner pattern as the kit.
   - Changing a copy without the source fails the test.
5. **The validator is hand-written** for the two fixed schemas (about 150 lines). No `jsonschema` dependency.
   - Why: the schemas are small and fixed, and home-mcp has two dependencies today.
   - Rejected: `jsonschema`, a new dependency for one use.
6. **Manifests are JSON, written by hand and reviewed by PR.** One file per initiative, `docs/missions/<id>.json` in
   pi-hub, holding:
   - the initiative;
   - stages and their gates (criterion text and required evidence kinds);
   - workstreams, tasks and dependencies;
   - decisions already answered, as text plus the spec line that records the answer;
   - risks;
   - evidence refs (repo, path, commit, or a PR number).
   It is never parsed from spec prose (§19 M6).
7. **Event ids are deterministic:**
   - **Importer events:** `uuid5(namespace, "<manifest path>@<commit>#<entity id>#<event type>")`. Re-importing the same
     commit is a no-op, and a new commit yields new events. These become a proposed revision at M1b (§8).
   - **Hook events:** `uuid4`, written into the spool line once. A drain that retries resends the same id.
8. **Model detection** (§21.1):
   - The hook reads at most the last 64 KB of `transcript_path` for the newest assistant line's `message.model`, and
     sends only that id string, or null.
   - It sends `effort.level` as the reasoning configuration.
   - For a subagent, `resolvedModel`, `totalTokens` and `agentId` come from the Agent tool's PostToolUse response.
   - Nothing else is read from the transcript.
9. **Attach and lineage.**
   - `/mission attach <initiative> [workstream]` writes `~/.claude/mission-attach.json`, keyed by the real path of the
     cwd, with the session id, branch and remote.
   - A SessionStart whose cwd is already attached re-binds and adds the old session id to its lineage. Its `source` (a
     new session or a resume) only goes in the event.
   - `/mission detach` removes the binding.
   - Only attached sessions emit events (D3).
10. **What the hook sends** (D9, §21.1). Per event:

    | Event | From |
    |---|---|
    | `session.attached`, `session.ended` | the attach skill; SessionEnd |
    | `turn.started` | UserPromptSubmit, with `prompt_id`. The prompt text is never sent |
    | `turn.finished` | Stop |
    | `tool.running`, `tool.finished` | PreToolUse, PostToolUse: label from `describe()`, `tool_use_id`, `duration_ms` |
    | `waiting.owner` | PermissionRequest: the tool name and label only |
    | `subagent.started`, `subagent.finished` | SubagentStart, SubagentStop: `agent_id`, `agent_type` |
    | `evidence.reported` | `git commit` / `gh pr create` detected in PostToolUse: sha or PR number from `tool_response`, parsed by fixed patterns |
    | `task.started`, `task.done` | the skill |

    Each event also carries `model`, `effort`, `branch` (from `git -C cwd branch --show-current`, 1 s timeout) and
    `remote`.

    Never sent: `prompt`, `tool_input` beyond the label, `tool_response` beyond the sha or PR pattern,
    `last_assistant_message`, or any transcript text.
11. **One label function.** `describe()` moves out of `localai-progress.py` into `home_mcp/mission/labels.py`, and both
    hooks use it.
    - The install step (owner, step 6) replaces the copy in `localai-progress.py` with an import from the installed
      path.
    - Rejected: a second copy of `describe()`.
12. **Keys.** The drainer reads Keychain items `pi-hub-mission-claude-key` and `pi-hub-mission-importer-key`, with a 2 s
    timeout, reusing `decisions.hub_key()`'s argv shape (generalised to take an item name).
    - The keys themselves are made on the Pi by `deploy-key.sh` and stored in the Keychain in M1b. That is an owner
      step.
    - No key means the drain keeps the spool and exits. The reason goes to `~/.claude/mission-drain.log`, without the
      key.
13. **What the importer imports from print-lab.** Only experiments a manifest names (`experiments: ["hex-tile/E-007"]`).
    - They are read through `git -C <print-lab> show origin/main:<path>` after a `git fetch`, never from the working
      checkout (see "~/dev checkouts lag origin").
    - Fields taken: `id`, `question_text`, `hypothesis`, `prediction`, the findings count, and the record's commit.
    - An experiment the manifest names but print-lab lacks is an `unavailable` result with its id. It is never skipped
      silently.
14. **home-mcp `decisions` v2** (§7.4, §9.2):
    - It asks `GET /api/decisions?v=2`. While Pi Hub doesn't serve v2 (today it ignores the query), the result is the
      A33 shape and is reported `version: 1`.
    - Every text field is wrapped: question, options' label, summary, benefits, drawbacks, risks and consequences,
      recommended, context, `why_needed`, rationale, and answer notes.
    - A row with an unknown `kind`, or a bad plain field, is dropped. Its id goes in `errors` as `bad_row`, and the rest
      of the read stands. If the whole body is malformed, the read fails as today.
    - Rejected:
      - Failing the whole read on one bad row, as today: one structured row would blind every session (review M4).
      - Silently skipping the row.
    - The legacy A33 read's tests stay and pass unchanged.

### Step 6 (owner): install on this Mac

Run `scripts/install-claude-mission.sh`. Then the owner adds the printed hook entries to `~/.claude/settings.json`:
- `mission-report.py` on SessionStart, SessionEnd, UserPromptSubmit, PreToolUse, PostToolUse, PermissionRequest,
  SubagentStart, SubagentStop and Stop;

- `async: true` on every event except PermissionRequest. That one stays synchronous because it is a no-op return; this
  is the writer's call.

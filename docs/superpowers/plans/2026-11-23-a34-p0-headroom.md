## Decisions this plan makes (for the owner's review)

None changes the spec. If the owner disagrees with one, it changes here.

1. **Tests use a cheap password hash; production keeps its own.** A new `tests/conftest.py` lowers the scrypt cost for
   the test process only (by patching the cost constant in `hub/auth`, not by an environment variable the service could
   read). A test pins the production cost (`n=2**14, r=8, p=1`) so the shortcut can never reach the hub. This removes
   ≈210 s on the Pi. *Rejected:* sharing one signed-in hub across tests (module-scoped fixtures). That is faster still,
   but it lets one test's state leak into the next, which these files deliberately avoid.
2. **Release tests keep running the real script, with less repeated work.** `test_release.py` builds its git repo and
   tarball once per module and copies it per test, instead of building it in each test. *Rejected:* mocking the script.
   These tests are the evidence that a release rolls back correctly, and they only mean something against the real
   bash.
3. **Fixed waits become events.** The preview servers shut down with a short poll interval; the "slow Local AI" test
   uses a fake that blocks on an event the test releases, not a 5 s sleep. Same assertions.
4. **The release shows its own test time.** The release record's message gains the pytest seconds ("Tests passed in
   612 s"), and above 600 s the release still goes live but says "tests over budget". This is evidence, not a new
   gate: the 900 s limit stays the only stop (D8). *Rejected:* failing a release over 600 s. That would turn a budget
   into an outage.
5. **A per-phase ceiling is measured the same way each time:** the release's own reported seconds, never a Mac number
   scaled up. The Mac numbers in this plan only rank the causes.
6. **Local AI's kit catch-up is delivered with A27 step 2's first part.** Syncing 2.27.1 means consuming 2.26.0's page
   list, which is A27 step 2's System page and Developer-tools cards. So P0's kit PR is "A27 step 2a": sync the kit,
   draw the System page with its five cards and Developer tools with its tool cards (from the spike), and answer the
   retired ids through `redirect(id)`. The Activity view (A27 step 2b) stays a separate PR before A34's P4, as A34 says.
   *Rejected:* syncing the kit and leaving Local AI on its old page list. The kit's own build check would then disagree
   with Local AI's registry, which is the drift A27's plan warns about.
7. **No parallel test runner on the Pi.** pytest-xdist would need installing on the Pi (a host change), per-worker
   databases, and would compete with the live services on 4 cores already at load ~9. Considered only if steps 1-3
   don't reach the budget, and then as its own owner decision.
   **Answered 24 Nov 2026:** owner chose pytest-xdist after releases of 596, 589 and 628 s (fa4436a, Pi at 75 °C,
   load ~9, camera ffmpeg ~200% CPU during a print).

## Acceptance

P0 is accepted when three consecutive Pi Hub releases have reported test times under 600 s and Local AI's live build
reports the current kit. Recorded in `docs/operations.md` under "Pi Hub draws the Assistant (A34)" as "P0 accepted
<date>" with the three release commits and seconds. A matching SHA on the Pi is a deploy, not acceptance; nothing marks
P0 done before that record.

## Out of scope (noted, not gated)

- **The Pi runs hot during releases** (79 °C, load ~9 on 23 Nov). The tests share the CPU with the live services. A
  cooling or scheduling fix is a hardware/host question; follow-up: a `pi_health` check of throttling during the next
  release, filed as a pi-hub issue if the Pi throttles.
- **The 120 s limit on the JavaScript tests** (`deploy/pi-hub-release:121`): not measured here; step 4 reports it too so
  it doesn't become the next surprise.
- **SD card at 78%**: unrelated to time, but tests write under `/var/tmp` on it. Tracked by the existing disk checks.
- A27 step 2b (the Activity view) stays A27's, before A34's P4.

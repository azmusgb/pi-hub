## Decisions this plan makes (for the owner's review)

None changes the spec. If the owner disagrees with one, it changes here.

1. **One package, `hub/missions/`.** `contract.py` (reads `docs/contracts/mission-events-v1.json` once at import and
   validates against it), `log.py` (append, idempotency, rate limit), `project.py` (pure projection functions),
   `store.py` (the tables), `views.py` (read shapes), `github.py` (the reader), `routes.py`, `__main__.py` (`rebuild`).
   - Why: the spec names `python -m hub.missions rebuild`. The contract file stays the one source; the validator reads
     it, so the contract and the code can't drift.
   - Rejected: a hand copy of the contract in Python (two owners of one thing).
2. **The projection is one pure function, used live and by `rebuild`.** `apply(state, event) -> list[change]` over an
   in-memory view of one initiative. The live path applies it inside the event's transaction; `rebuild` replays the
   log through the same function into fresh tables. So "rebuild = live" is a property of one function, and the test
   compares the two table sets row by row.
   - Rejected: SQL triggers (untestable without SQLite, and a second implementation for rebuild).
3. **Tables.** `mission_events(seq INTEGER PRIMARY KEY, event_id UNIQUE, at, received_at, source, initiative, entity,
   type, body, late)`; projections `mission_initiatives`, `mission_revisions`, `mission_changes` (the per-revision
   change-sets), `mission_entities` (stage, gate, workstream, task, dependency, risk, decision-import, experiment: one
   table keyed by child id, with `kind`, `revision`, `data` JSON and `state`), `mission_evidence`, `mission_executions`.
   Names beyond the spec's are the builder's (§20).
4. **Execution rows are updated in place; only state changes are appended** (§6.2). `tool.running` and
   `tool.finished` update `mission_executions` (label, `last_event_at`, tool start) and are **not** appended to
   `mission_events`, so they are outside rebuild. `rebuild` therefore rebuilds executions to their last **logged**
   state and keeps each row's in-place fields. The rebuild test compares the logged columns only, and names the
   in-place ones.
   - Trade-off: after a rebuild, an execution's tool label can be older than its log; its freshness, which is computed
     from `last_event_at`, is not affected.
5. **Late events never move an execution backwards.** An event whose `at` is older than the execution's
   `last_event_at` is logged (with `late`) and changes no execution field. Order shown to clients is always `seq`.
6. **Per-source keys live in `hub/missions`, not in `KEY_FOR`.** `KEYS = {"claude": "mission-claude", "importer":
   "mission-importer", "localai": "localai"}`, checked with `releases.host_key_ok`.
   - Why: `KEY_FOR` maps release **targets** to keys, and `key_ok(target)` would then let a mission key post a release
     report for a target named `mission-claude` if one were ever added. The spec's "added to `KEY_FOR`" is about which
     keys exist, not where the map lives.
   - `deploy/deploy-key.sh` accepts `mission-claude` and `mission-importer`, and stores them in the Keychain as
     `pi-hub-mission-claude-key` and `pi-hub-mission-importer-key`, the names `drain.py` reads.
   - A source may write only its contract types, and only executions it created (§7.4). Ownership is
     `(source, session_id)` for `claude`. This is a mistake guard, not a trust boundary (§5).
7. **Rate limit: per source, in memory, 60 events a minute** (contract `limits`). Over it: 429 with `Retry-After`.
   "After repeated refusals" (§13) is, by this plan's choice, 10 refusals of any 4xx from one source inside 10
   minutes; it raises the Needs item `pi:missions:<source>:refused` (tone `attention`), which clears after an hour
   with no refusal. The counter is in memory, so a restart clears it; refusals are also logged.
8. **Freshness is computed when a read happens** (§7.5), by one pure function `shown(execution, now)` →
   `{state, label, live: bool}`:
   - `running_tool`: "Running a tool for N min" (no window);
   - `working`: live for 2 minutes from `last_event_at`, then "No report since HH:MM";
   - `turn_finished`: "Turn finished HH:MM" (never "waiting on you");
   - `waiting_owner` (from `waiting.owner`, §21.1): "Waiting for you since HH:MM", same 2-minute rule after the next
     event;
   - `ended`: "Ended HH:MM";
   - `unknown`: "No report since HH:MM", or "No report yet" when there is none.
   - Every response carries `as_of` (the server's now). The page relabels every 15 s from `as_of` plus its own elapsed
     time between polls, so a silent source can't stay "Live" (§17.1 timer test).
9. **Reads poll, never stream** (§13). `GET /api/missions/{id}/changes?after=<seq>` answers the views' changed parts
   and the new `seq`; the page polls it every 10 s while visible, with ETag (`"<seq>"`) and 304. A test asserts no
   `text/event-stream` route under `/api/missions` and no `asyncio.to_thread` in the package.
10. **The owner route in M1b takes three verbs:** `revision.accept`, `revision.reject`, `initiative.status`. Gate
    verdicts, manual evidence and Commands are refused with 400 "not yet" until M3/M4 add them.
    - Owner session, and `Sec-Fetch-Site: same-origin` **required** (§13 "Writes need"). A33's answer route allows a
      missing header; this route does not.
    - Each write is conditional (accept only a revision that is still `proposed`, at the revision number the owner
      saw), so a double tap is a 200 that changes nothing. It is logged in `action_log` and appended as an event with
      `source=owner`.
    - **One tap accepts A34** (§8 "One owner tap accepts it") through `revision.accept`. The `approve` decision kind is
      M2, so M1b does not create a Decision for the import; M2 moves revision approval onto it.
11. **Decisions v2 (A33 extended, §9.1), additive.**
    - New nullable columns: `initiative, context, why_needed, requested_by, rationale, evidence, confidence,
      reversibility, affects, blocking, status, number, delegable, default_if_delegated, digest`. Old rows are
      unchanged.
    - M1b accepts new kinds `multi` and `yesno` only. `multi`: 2-8 options, answer a non-empty subset in option order,
      stored as a JSON list. `yesno`: no options sent; stored options `["Yes", "No"]`. D7's widened limits (8 options,
      2000-character context, 32 KB body) apply only to a row with `initiative`; A33-shaped rows keep 4 options and
      8 KB.
    - Options stay strings in M1b. Option objects (`summary`, `benefits`, …), `rank`, `number`, `approve`, the digest
      check, immutability and delegation are **M2** (§15). The `digest` column is added now, empty, so M2 needs no
      second migration.
    - `GET /api/decisions` (no `v`): returns only rows an A33 client can read: kind `choice|text`, no `initiative`.
      `GET /api/decisions?v=2`: every row, with `"version": 2` in the body. Both need the Mac key, as today.
    - A decision with `initiative` is exempt from the 50-row trim (§6.2) and is mirrored into the log as
      `decision.asked` / `decision.answered` events, `source=pi-hub`, outside rebuild (decisions stay authoritative
      themselves).
    - Home's Needs you keeps drawing every open decision through the kit, which draws the new kinds once the kit step
      is synced; until then the kit draws them disabled with its own reason.
12. **The GitHub reader** (D10, §7.2):
    - **Token:** a fine-grained, read-only token (Pull requests: read, Checks: read, Commit statuses: read, Metadata),
      for the repositories named by open initiatives, at `/etc/pi-hub/secrets/github_token` (root:pi-hub 0640). Made
      and installed by the owner. Never logged, never in a response.
    - **What it reads:** only PRs named by evidence (`pr_ref` or a reported `evidence.reported` with `pr`) of an
      initiative whose status is `proposed`, `active` or `paused`. Identity is `(repo, pr)`.
    - **Pace:** one thread, a pass every 120 s, first pass 30 s after start. Each PR gets at most one **read** per
      pass: `GET /repos/{r}/pulls/{n}` (state, merged, head SHA), and, only when that answered, `GET
      /repos/{r}/commits/{sha}/check-runs`. Both carry `If-None-Match`; a 304 is free against the rate limit.
      - This reads the spec's "≤1 request per PR per 2 min" as one PR read (two ETag'd calls), not one HTTP request.
        The alternative, alternating the two calls between passes, doubles the time to see a finished check
        (to 4 min). Recommended: the PR-read reading; the owner can choose the other.
    - **Outcomes, stored per PR** in `mission_github`: `ok` (state, merged, head SHA, each check's name and
      conclusion, `read_at`), `absent` (404: "Not found on GitHub"), `refused` (401/403: "GitHub refused the token"),
      `unavailable` (network, 5xx, rate-limited: "Not checked since HH:MM", keeping the last good read labelled as
      such), `unconfigured` (no token file: "GitHub not set up"). The raw response is never stored.
    - **Evidence:** each `ok` read whose checks have all finished writes one evidence row, kind `ci`, trust
      `trusted`, digest = head SHA, summary "n passed, m failed of k checks", `observed_at = read_at`. A new head SHA is
      new evidence; the old row stays.
    - **Lifecycle:** one exception boundary per pass; no overlapping passes; `last_pass_at` is part of the sources line;
      two missed passes show "GitHub reader stopped since HH:MM".
    - **Latency:** a check that finishes is on the page within 120 s (pass) + 10 s (page poll), plus GitHub's own lag.
    - Nothing becomes `verified` in M1b (that is M3); the reader only produces trusted evidence.
13. **The release test field.** `releases.valid()` accepts an optional `tests: {python_s, js_s, workers}` (integers,
    0-3600, workers 1-16). `deploy/pi-hub-release`'s `report()` sends it for `deployed`. The pi-hub release record
    becomes trusted evidence, kind `release` (with `tests` when present), for any initiative whose manifest names
    pi-hub evidence of kind `release`. Other targets may send the field later; none has to.
    - `deploy/` changes only in a PR that names the decision allowing it: this one is A35 §14 ("add the field (M1b)").
14. **Pages and the registry.**
    - The kit's `pages.json` gains `missions` (`/missions`) and `mission` (`/missions/<initiative>`), both System
      `detail` rows whose parent is Versions: `missions` is reached from a card on Versions, the palette and the map;
      `mission` from a row on `/missions`.
      - Why a detail: the registry requires every `page` to be on its area's strip, and System's strip is at its cap of
        eight (A22 2.2, A27 D3). Raising the cap is a baseline change. Versions is the nearest parent: it already
        holds the release records A35 uses as trusted evidence.
      - Rejected: a ninth strip page (needs an amendment to A22's cap); a Health card (Health is about the Pi, not the
        work).
    - The kit's registry learns one templated hub address: a `detail` path may end in one `<value>`, the convention the
      Assistant's `/assistant/run/<id>` already uses. Pi Hub's `_shell_paths` matches it as a pattern
      (`[a-z0-9][a-z0-9-]{1,39}`), never as a literal.
    - `/missions/<id>` has three of the five §10.1 tabs in M1b: Overview, Decisions, Evidence. Plan and Work arrive in
      M3. `ui-tabs` takes 2-5, so three is fine, and the tab strip never shows a tab that does nothing.
    - Page JS ≤ 20 KB gzipped (§13), measured in the PR.
15. **The summary view is frozen here** (`GET /api/missions/{id}?view=summary`, Mac key or Local AI key; read by
    home-mcp `mission` and Local AI's server in M5). Shape version 1:

    ```json
    {
      "view": "summary", "version": 1, "as_of": "<iso>", "seq": 1234,
      "initiative": {"id": "a34", "title": "…", "status": "active",
                     "manifest": {"repo": "azmusgb/pi-hub", "path": "docs/missions/a34.json", "commit": "<sha>"},
                     "revision": {"n": 1, "status": "accepted", "at": "<iso>"}},
      "stages": [{"id": "a34:stage:p0", "n": 0, "title": "…", "status": "active",
                  "gates": [{"id": "a34:gate:p0", "verdict": "open"}]}],
      "workstreams": [{"id": "…", "stage": "…", "title": "…", "repo": "owner/name",
                       "tasks": [{"id": "…", "title": "…", "state": "done", "trust": "reported"}]}],
      "dependencies": [{"from": "…", "to": "…", "kind": "blocks", "status": "open"}],
      "decisions": {"open": 2, "blocking": 1, "answered": 14, "open_ids": ["…"]},
      "executions": [{"id": "…", "provider": "claude", "level": "observable", "state": "working",
                      "label": "Running tests", "last_event_at": "<iso>", "live": false,
                      "shown": "No report since 09:40", "tasks": ["…"]}],
      "evidence": {"trusted": 18, "reported": 6, "imported": 9, "owner": 0},
      "sources": [{"name": "ledger", "state": "ok", "as_of": "<iso>"},
                  {"name": "github", "state": "unavailable", "as_of": "<iso>"}],
      "untrusted": ["initiative.title", "stages[].title", "workstreams[].title", "workstreams[].tasks[].title",
                    "executions[].label"]

    ```

    - `untrusted` lists every field a source wrote; readers draw them as text, and home-mcp wraps them.
    - Additive fields need no bump; a removed or renamed field bumps `version`, and Pi Hub serves N and N-1 for one
      release (the contract's rule).
    - A read that fails is a 503 with a reason, never an empty summary. An unknown initiative is 404.
16. **Test seconds.** Every new test is a pure function or an in-memory SQLite test; no thread, sleep or network.
    Each PR states its new tests' seconds on the Mac and an estimate for the Pi (×3, from the last release's ratio);
    H9 reads the real number from the next release message. The M1b total stays ≤ 15 s.
